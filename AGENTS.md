# Final Frontier — Web Frontend

Next.js rebuild of the legacy `ff-site` React app. Lore archive + authoring UI for a sci-fi TTRPG universe; consumes the `ff-server` Express/Prisma API.

## Environment
- **Node 22 via nvm required** (system node is 18). Run `nvm use` (there's an `.nvmrc`) before any npm/next command.
- Two dev servers: ff-server API on **:3000** (`npm run dev` in `ff-server/`), this app on **:3001** (`npm run dev` here). `NEXT_PUBLIC_API_URL` points at the API (see `.env.example`).
- ff-server's dev script runs `tsx watch` — it auto-restarts on save.
- **Versions come from git tags** (footer + `/api/version`): put `[minor]` or `[major]` in a PR's title/description to cut a release when it merges; otherwise every merge is a patch. See `docs/versioning.md`.
- Production builds use a separate distDir (`.next-build`) so `npm run build` can't corrupt a running dev server.

## Workspace
- `ff-site/` and `vortox-bot/` are **symlinks to legacy repos** — reference only, gitignored, excluded from tsconfig. Never import from any symlink.
- `ff-server/` is also a symlink but is the **live API we actively develop** — it's a separate git repo; commit its changes there (`git -C`), separately from this one.
- Requirements live in `ff-server/FF design document.md` (FR-* / NFR-* ids). The ff-server Prisma schema is the canonical data model; `src/lib/types.ts` mirrors it. Schema changes go through `prisma db push` (no migrations dir).
  - All FR-* requirements are fulfilled. FR-AUTH-4's "display name" was deliberately dropped: usernames are fixed (the archive import maps players by username) and there's no separate display name.
- `archive-to-markdown/` is the episode-import pipeline (Discord export → markdown → API JSON → `/import` page). See its README before touching import/conversion.
  - The `/import` page is open to **any member** (who is always credited as an author; replacing a story's text is for its authors and admins) and renders a **preview** with the real `StoryReader` (`preview` mode: no links, anchors or NPC naming) before upload, and won't upload while any NPC quote is unnamed. Stories go straight to the shelf; there are no drafts. When the form's slug matches a story with a stored `importMeta` (the color → speaker map of its last Google Doc import), `DocxStoryForm` pre-fills those colors and marks the rest "new"; picks made in the form win. A doc's pictures convert to `IMAGE` lines (`meta.images`): the importer lists them with a booru post # field each (checked via `GET /booru/:id`; blank = left out), since story pictures live on booru.vortox.space, never in the DB. The reader shows `StoryLine.imageUrl` through `imageSrc` (the booru proxy).
  - The `/import` page is **story-only**. Admins import and update episodes on the **`/admin`** page (navbar "Admin", admins only): pick md-to-api.py's JSON files, it previews (new / update / unchanged per episode, conflicts, missing players, NPC voices to create), then dry-runs or imports them all in one transaction (ff-server `POST /admin/episode-import`). An episode whose season and number are already in the archive is **updated in place** (`src/jobs/episodeImport.ts` + `messageAlign.ts` in ff-server): its messages are lined up with the file's, so commentary notes follow their message (a removed message's notes go to the nearest kept one), a line whose file names no persona keeps its stamp, and times stay on the clock they were stored on (the file's times have no zone). This is how markdown fixes reach prod. The same page runs ff-server's maintenance jobs (story hashes) and shows every run's log. It also updates **Vortox Machina** from Discord (`VmImportPanel` → ff-server `/admin/vm-import`, `src/jobs/vmImport.ts`): pick a DiscordChatExporter JSON export of #cyoa-vm; the GM's entries posted after the last import are appended (the page only uploads those), with a preview, a dry run and the History log. The last message read and the speaker codes (E = Emmett, ...) live in ff-server's `app_settings`; a new code is asked for once in the preview, then remembered. No Discord token on the server. ff-server's `append-vm-from-discord.ts` is the same import from the CLI (an export file, or the local discord-mcp). Committing markdown here never changes the live archive: the site reads the production database, so new and edited episodes still have to be imported there. It and `story-md-to-api.py --upload` send each story as one request to ff-server's atomic `POST /stories/import` — nothing partial can be left behind, so there's no eject/rollback UI; a 409 means it's already on the shelf. The CLI uploaders (`api-import.py`, `episode-json-upload.py`) still work on dev machines via the chunked append endpoints, but `api-import.py --replace` deletes the episode first, taking its commentary notes with it.

## Analytics and logs
- **Views** (`src/lib/views.ts`): episode pages and story/chapter pages call `recordView(kind, slug)` once the page is known to exist. It posts to ff-server's `POST /views` from Next's `after()`, passing the session token so the server can count signed-in and anonymous views in separate columns. Counts only, never who read what (the user's call, 2026-11-07). The /admin page's Views panel reads `GET /admin/views`; its Server log panel reads `GET /admin/logs` (ff-server's in-memory log buffer).

## Architecture
- **Production** (NearlyFreeSpeech, FreeBSD; see `ff-server/docs/deploy-nfsn.md`): one origin, where the site proxy sends `/api/` to ff-server and everything else to this app. So the site's own route handlers live under **`/site/`** (`/site/auth/*`, `/site/ff/*`), never `/api/`. `next.config.ts` builds a standalone server (`output: 'standalone'`) with `images.unoptimized` (sharp has no FreeBSD build). `src/lib/api.ts`: server code reads `API_URL` at runtime (loopback to ff-server in prod), browser code `NEXT_PUBLIC_API_URL` (built as `/api`). Merging to `main` deploys via GitHub Actions, which runs `scripts/deploy-nfsn.sh` (builds HEAD in a temp worktree and restarts the `ffsite` daemon); see the runbook's "Deploying".
- **Auth**: the ff-server JWT lives in an httpOnly cookie `ff_token`, set by the `/site/auth/*` route handlers. Server components call `getSessionUser()` / `getToken()` (`src/lib/auth.ts`); client components read `useSession()` and send authenticated API calls through the generic proxy `/site/ff/[...path]`. Browser JS never sees the token.
  - Password changes go through `/site/auth/password` (not the proxy): ff-server revokes every older token and returns a fresh one, which that route swaps into the cookie.
  - `SessionUser.mustChangePassword` (seeded/reset accounts): `PasswordChangeGate` (in the root layout) pins the user to `/account` until they change it; ff-server refuses their writes meanwhile.
  - Admins see a "Reset password" control on a player's `/users/[username]` page (`ResetPasswordControl` → ff-server `POST /users/:id/password-reset`): back to the default password, forced change, every session signed out. Not shown on admin profiles.
  - Character and persona avatars can be uploaded (`AvatarField`, `AvatarUploadButton`, `src/lib/avatarUpload.ts`): PNG, at most 14x14 and 16 KB. The picked file goes up as a `data:` URL in the record's normal `image` field, and ff-server stores it and writes back `/api/avatars/<sha256>.png`, which `imageSrc` routes through `/site/ff`.
  - `/account` edits the user's own profile (bio, wiki username, booru avatar by post ID) and password; `/users/[username]` is the public profile. Link people with `UserLink`.
- **Reconstructed episodes**: `Episode.reconstructed` marks episodes rewritten from memory, not recovered from logs (FF1's lost early episodes, manuscripts in `archive-to-markdown/md/ff1/reconstructed/`, `"reconstructed": true` in `meta/ff1.json`). They're stored before the archive (FF1 episode_no -3..0) with no message timestamps (undated `**Account**` headers in the markdown), show as "R1"…"Rn" via `episodeNumberLabel` (`src/lib/seasons.ts`) with a "reconstructed" tag, and never count as a character's first appearance when an archived episode exists.
- **In-universe dates are GUY calendar integers** (equinoxes since the GUY epoch; 1 equinox = exactly 1 Earth day), e.g. `Character.dob`. Use `src/lib/guy-time.ts` — an identical copy lives at `ff-server/src/utils/guy-time.ts`; keep them in sync. Real-world timestamps (messages, playedDate) stay DateTime.
- **User rich text** (character blurbs, item descriptions, bios, commentary) is stored as ff-server-sanitized HTML with plain text entity-encoded: render it with `RichText`, never as a text node (that shows `&amp;`). Editors decode it for the textarea (`richTextField` in the editor schemas, `decodeEntities` in `src/lib/html.ts`).
- **Record editing is schema-driven**: field definitions live in `src/lib/editor/schemas.ts` (`EDITOR_SCHEMAS`); `RecordEditor` renders/validates/submits any registered kind. Add fields there, not in per-page forms.
- **`/search`** is server-rendered from URL params: `sort` (`first`/`last` = archive order via ff-server `sort=appearance&dir=`, default best match), `exclude` (season slugs), and a page param per section (8 rows each). Transcripts, stories and commentary come from ff-server's paginated `GET /search?category=` (messages|storyLines|commentaries), whose hits carry season and speaker fields for the season tags and avatars.
- **Category search** (FR-SR-1) uses the shared `IndexScan` component; season/episode slugs and deep links come from `src/lib/seasons.ts`.
- **Story categories**: a story's branch comes from its campaign's `Season.kind` (`storyBranch` in `src/lib/stories.ts`: MAINLINE/PLANNED = mainline, SIDE or no campaign = spin-off) and `Story.canon` (default true; `canon: no` in manuscript frontmatter, the import form's non-canon box, or an admin's "shelf settings" on the story page). Vortox Machina is the story-only SIDE season `VM` (ff-server `npm run seed:story-shelf`, which also marks the known non-canon stories), hidden from the Archives roster like T&L. `/stories` filters by season (one chip per season on the shelf) and canon status, and tags each card with its season code and canon status; story stats are word counts (`wordCount`, from ff-server), not line counts.
- **Player characters (campaign cast)**: ff-server `GET /seasons/:season/cast` finds a campaign's player characters from its transcripts: in each episode, every player's most active character (QUOTE + ACTION messages). A player's main leads nearly every episode they attend; a side character (Bail, Ibraxas) only the episodes it carried. Nobody is excluded, so in FF4 (the only campaign with a GM) the GM's busiest NPC per episode counts too; admins curate those (demote to NPC). Admins can also add characters per campaign by hand (`Character.mainIn`, `SpeakerAdmin` → "add to cast…" → `PUT /characters/:id/main-in`): the only way a story-only campaign gets a cast. `/archives/[season]` lists the cast as avatars (`CastAvatar`, name on hover), most messages first; each episode page lists the ones that led it.
- **Character colors**: `Character.color` is the dark-mode color, `Character.colorLight` an optional light-mode override. Always resolve display colors with `characterColor(name, color, mode, colorLight)` (`src/lib/characterColors.ts`): each theme takes its own color, then the legacy table, then the other theme's color made readable (`suggestColorFor` in `src/lib/colorContrast.ts`: same hue, lightness moved in OKLCH until 4.5:1 on that theme's backgrounds), then the name hash. The character editor's two color fields (`theme` in the schema) show that resolved color when empty (in the picker and as the hex placeholder), so the suggestion and the site always agree. The editor draws them as one control (`ThemeColorPair`, with a transcript-block preview per theme and the characters with a similar color, `SimilarColors`); the lock between them (editor state only, not stored) ties the two: locked, editing either sets the other to it made readable for that theme; it starts unlocked when the two were picked separately (or the legacy table supplies the light color). A color under 4.5:1 gets a "use suggestion" button (the nearest readable version of the picked color). Look colors up by the character's own name, never a persona's display name.
- **Character index**: `GET /characters` returns `quoteCount` and per-campaign first `appearances`; `CharacterIndex` sorts by them (`src/lib/characterSort.ts`; default: times quoted, most first, since there's no "main character" field) and can group by campaign, where a character is listed under every campaign they appear in.
- **Galaxy map** (`/galaxy`, `src/components/galaxy/`; ff-server `src/galaxy/`, routes under `/galaxy/`): one page, `src/app/galaxy/[[...path]]/page.tsx`, whose address says what is open: `/galaxy?at=rsjeno_base` a place picked on the galaxy, `/galaxy/sol` a system's own view, `/galaxy/sol/earth` a body picked in it (a thing with no slug goes by `system-22` / `body-51`; an address naming nothing is a 404). `readAddress` / `addressUrl` in `data.ts` turn an address into what is open and back; the store starts from the page's address and then keeps the address in step with native `history.pushState` (opening or leaving a system) or `replaceState` (picking something else), and follows Back and Forward (`popstate`). The page loads every place (`GET /galaxy/places`: systems and landmarks with their bodies and travelogue) and hands them to `MapApp`. `data.ts` holds the Sector Grid frame math (klyr, Sagittarius A at the origin), the regions (read from `public/galaxy/territories.png`), the reference scales and `fromApi`, which turns ff-server's rows into the `Place`/`Body` shape the components use; its `STAR_TYPES`, `COMPOSITIONS` and `LANDMARK_CATEGORIES` keys must match ff-server's `galaxy.validation.ts`. `store.ts` (`useGalaxyStore`) keeps the places in step with ff-server through `/site/ff/galaxy/...`: every change is sent first and shown from the answer, except a body's slider edits, which show at once and are sent when they pause; a refused change shows its message (`store.error`). `GalaxyScene.tsx` is three.js with DOM markers on top; the galaxy itself is a painted disc under a few thousand large soft camera-facing clouds with real thickness (`galaxyClouds`, drawn instanced by `puffMesh`: bulge, bar, arms, dust lanes, halo; each several klyr wide so none reads as a place, and never star points): "Rotate" is OrbitControls, "Top-down" is locked (the frame loop puts the camera straight above its focus every frame, +y up; a drag never moves it, though picking a place or Recenter still slides it), and flying to a place slides the camera with its focus (not in Top-down while the whole galaxy is in view: the place is already on screen). In both views the wheel or a pinch zooms to the pointer (`zoomToCursor`; the wheel over a marker is passed on to the canvas), and the focus stays on the galactic plane (`screenSpacePanning` off). Behind it all is the site's starfield (`loadStarfield`, `buildSky`): a skybox cube kept on the camera in Rotate, the same tile laid flat on the screen in Top-down and in the still picture; the system view and the no-WebGL page use the CSS `--starfield`. How strongly the stars show is a view setting (`store.sky`, 0 to 1, default 0.25, the "Stars" slider; `--sky` on the map's root carries it to the system view). The view buttons are pictures (`ViewButtons` in `MapApp.tsx`: Rotate, Top-down, Recenter; names as tooltips): on a wide screen they sit in the view settings panel (`ViewSettings`: the layers list, which folds, then the view buttons and the Stars slider, which stay); on a phone one row under the search box holds the add button, the view buttons and a layers button that opens the list and the slider. The view settings (camera, layers, stars, orbit motion) are kept in localStorage under `galaxyView` and restored by `useGalaxyStore` on mount; `MapApp` draws nothing until they are in (`store.restored`), so the defaults never flash by. For a signed-in member, a click on empty space hangs a "+ Add here" button over that spot (`spot` in `GalaxyScene.tsx`, `onAddAt`), which opens the add wizard with the position filled in (`CreateFlow`'s `at`). A planet's or moon's details are headed by its textured disc (`BodyPortrait`). `SystemView.tsx` is the full-screen view of one system: its diagram zooms to the pointer with the wheel or a pinch and slides with a drag (`cam`, never smaller than the view), and its bodies travel round their orbits (`time`, a clock that only runs while `store.motion` is on, so the pause button leaves them where they are; periods follow Kepler with a square root taken so the outer planets still move). Bodies are numbered by `designate` in `data.ts` (run by `fromApi`, and again after a slider edit): planets count outward from the star, never below a stored `ordinal` ("this is planet N", the Planet number stepper in `BodyFields`), a planet's moons are lettered (a to z, then aa, ab), and a station is its primary, then its build year and iteration (Sol-3.3016-02, Sol.3016-02 round the star; entered by the member in `BodyFields`'s "Built" field, never made up by the map; no designation until the year is set). Each body gets `num` and its GU designation `gu` (Sol-3, Sol-3a). The rules are `wiki/reports/astronomical-designations.md` in the workspace. A planet or moon may have no name and then goes by that designation (`unnamed`); a named one shows it after its name (`BodyName`). A **belt** (`kind: 'belt'`, ff-server `BELT`) circles a star, a planet or a moon; round a planet or moon it is a ring (`ring`, set by `designate`; `kindLabel` in `parts.tsx` says "Ring"). It has `orbit` (the middle of the band) and `width` in the same unit, AU round a star and km otherwise, and no size. Planets carry their number in their kind ("Planet 3", `kindLabel`), never a Roman numeral: those are the belts'. A system's **primary** (`primaryOf`) is a star or a **barycenter** of type `stars` (ff-server `BARYCENTER`): the point a co-equal pair orbits, its stars being its children (`componentsOf`). A barycenter of type `planets` takes a planet's slot and number, and its planets are the pair (Sol-3-A, Sol-3-B; the pair Sol-3-AB; its moons Sol-3-Aa, Sol-3-ABa). A star may also orbit a star as a **companion** (one primary still). With more than one star, `designate` letters the stars (the primary A, companions outward, a pair's stars heaviest first) and every designation goes through its star: Vortox-A-3 round A, Vortox-B-1 round a companion, Vortox-AB-1 round a pair. `starOf` is the star that stands for the system (the primary, or the heaviest star of the primary pair), `hostOf` the star or pair a body's orbit is lit and held by (physics: `habAU`, `zoneOf`, `yearDays` take a star type or such a `Host`), `orbitAU` a body's distance from its star through its parents, `unitOf` whether its orbit is in AU (round a star or pair of stars) or km. The diagram draws a primary pair going round its barycenter at the center, a companion star on its own dashed orbit carrying rings for its planets, belts and stations, and a pair of planets as two discs going round each other in their slot (its and its planets' moons ringed round both). A barycenter's icon is two filled dots chasing each other with trailing arcs, in the pair's colors (`pairColors`). A pair is highlighted as one: a ring round both partners (`.pairRing`, also the pair's hit area) when the pair is pointed at or picked, and a partner's own disc (`.part`, `.partDisc`) only when that partner is. A system's header shows all its stars overlapping, A in front (`SystemDot`). The system view's add buttons follow the selection: nothing picked (or a belt or station) shows only "+ Add", which opens the add wizard with no kind chosen; a star or pair of stars offers "+ Planet" (round it), a planet or pair of planets "+ Moon", a moon "+ Ring", and a star or planet not already one of a pair "Make it a pair". The wizard's kinds are cards with each kind's picture as the diagram draws it (`KindCards`, `KindPicture`), and under the name it shows the designation the new body would get (`wouldBe` in `data.ts`, from a dry run of `designate` with the draft added; a station has none until its year is set). Its `companion` kind adds a star round the picked star or pair, else round the primary. Where it goes is two choices, a planet's system (`systemId`) and the body anything else goes round (`bodyId`): systems and bodies are numbered separately, so one read as the other picked the wrong parent. Picking a kind always starts from the selection (else the system's primary or first planet). The "Where does it go?" lists are grouped (`BodyOptions`): This system first, by type, then other stars, pairs of stars, planets, pairs of planets and moons. "Make it a pair" opens `PairFlow`, whose hint names both the companion's designation and what the body becomes (`wouldPair`) (ff-server `POST /galaxy/bodies/:id/pair`: the companion, how far apart, and whether what orbited it now circles both; the orbits split the distance by mass). A belt takes no slot: its Roman numeral names the owned orbit its zone sits inside (Sol-V, inside planet 5; Sol-IX, beyond planet 8), and belts sharing a zone are .1, .2 outward (Sol-IX.1). A ring counts against its planet's moons (Sol-6-I inside moon a; Sol-3a-I for a moon's). A belt may go unnamed too. The diagram draws a star's belt as a band with lanes of dots that hold still (only planets, moons and stations travel; the user's ruling, 2026-11-16), placed among the planets' rings (`starBelts`, `BELT_LANES`), a planet's ring as a band in the slot a moon's orbit would take (with no name in the drawing), and a moon's ring as a thin band round its dot. The add wizard's "Belt or ring" kind (`CreateFlow`'s `kind`, the "+ Belt" / "+ Ring at X" buttons) circles the picked planet or moon, else the star; `BodyFields` gives it what it is made of (`BELT_TYPES`), distance and width, keeping the inner edge clear of what it circles (`beltWidthMax`, `ringRange`). For whoever may add, the diagram draws a dashed "+ add Sol-2" ring for every open number inside a numbered planet, which opens the add wizard on that slot (`PlanetSlot`), and behind everything a soft band over the star's temperate orbits (`habZone`, the bounds of `zoneOf`). Members never have to type raw numbers: sizes and orbits are picked against reference bodies, but a scale's readout is a button that turns into a number box (`Readout` in `parts.tsx`) for whoever knows the value. A moon cannot be put inside its planet's Roche limit, nor a station inside the planet (`rocheKm`, `satelliteRange` in `data.ts`; the site enforces it, ff-server does not). Planets and moons in the diagram carry a texture per type in a darker and a lighter shade of their color (`BodyTexture`). Any signed-in member adds (the + button; signed out it is a sign-in link); edit and delete controls show only to the place's creator and admins (`store.canEdit`; ff-server enforces it). A black hole is a system whose star is a `black_hole`, never a landmark. The travelogue (`Travelogue` in `parts.tsx`) lists the episodes tagged on a place or one body; any signed-in member tags one with "Tag an episode" (`EpisodePicker`, which filters the episodes of `GET /seasons`, loaded on first use by `store.loadEpisodes`), and the × on a tag shows to whoever tagged it, the place's creator and admins. "Edit" on a place or body shows its name, description and wiki slug (`TextFields`; a landmark's kind too), each saved when the field is left (`store.editPlace` / `editBody`); a place or body whose slug has a wiki page shows that page's picture, opening paragraph, faction and a link to the article under its own description (`Writeup`; `wikiInfo` in `data.ts` reads ff-server's `wiki` row, which comes from the wiki cache, so a new wiki page shows after `npm run refresh:wiki-cache` there). Name labels are decluttered each frame (`declutter` in `GalaxyScene.tsx`: right of the dot, else left, else hidden until hovered) so a label never covers another place's dot. The arms are laid out as the Milky Way's are (`ARMS` in `GalaxyScene.tsx`: Norma/Outer, Scutum-Crux, Sagittarius, Perseus, with Scutum-Crux and Perseus the major pair, plus the Orion Spur at Sol); the "Arm lines" layer (off by default, `buildTransit`) draws them as colored transit lines in the colors of the old subway-style map, with the Bakree and Omega routes run between saved places by slug (`ROUTES`). Without WebGL the map is one top-down picture, `public/galaxy/still.webp`, with the places laid over it (clickable, placing works, no camera and no layers); the picture is drawn by `renderStill` from the same groups as the live scene (`buildWorld`), so after changing how the galaxy, grid or territories look, open the dev-only page `/galaxy/still` and save what it shows over that file (`STILL_HALF` is the half-width in klyr the picture covers). **Drawing cost** (2026-11-16): the map draws a frame only when the camera has moved or something changed (`dirty` in `GalaxyScene.tsx`, set by every React render, a resize and each late-loading texture; the frame loop compares the camera with the one last drawn), and not at all under the system view (`paused`); anything new that changes the picture without a React render must set `dirty`. The clouds are drawn into a half-size picture of their own and laid over the disc (`cloudLayer`, `CLOUD_SCALE`; their blending keeps the background's share in alpha so this matches drawing them in place, which `renderStill` still does), and a puff that would fill the screen fades out (`span` in `puffMesh`). The sector readout is written straight to its node, not through state. In the system view the orbit clock is a ref, not state: each tick writes the `transform` attribute of the parts that travel (`mover` in `SystemView.tsx`, class `.mover`), so React does not draw the diagram again each frame, and it steps only `ORBIT_FPS` (15) times a second, since each step paints the diagram, and holds still during a zoom and for `ZOOM_REST_MS` after it (`zoomedAt`); wheel events are gathered into one zoom step per frame. Keep these plain SVG attributes: CSS transforms with `will-change` make each part a browser layer as large as its content times the zoom, drawn again at every zoom step, which ran LibreWolf (the user's browser) to 28 GB and froze the machine when tried; a planet's group is drawn about (0, 0) and carried along its orbit, its moons likewise inside it. No `filter` in the diagram (the star's glow and the temperate band are radial gradients, hover is a stroke): a filter there is redone every frame and grows with the zoom. Not built yet: seeding from the wiki.
- **Commentary notes** sit on a transcript message or a story line (a `commentaries` row has exactly one; `notesUrl` in `CommentaryThread` builds either's address). They show three ways: the rail beside each transcript block or story line (`CommentaryThread`; the rail is link, personas/voices (🎭, who may change them), notes, outside the text's box; a story line's rail shows on hover, and a line with notes keeps its count visible), an episode's list above its transcript, and a user's list on `/users/[username]` (ff-server `GET /users/:id/commentaries`, with story notes linking to their line); both lists use `NoteList`. Replacing a story's text (`PUT /stories/:slug/import`) keeps its notes: each moves to the new line with the same text, else the line at its old position (ff-server `src/story/note-carry.ts`). Note search still covers transcript notes only. Same-page `?line=N` links use `LineJumpLink` (pushState, no transcript refetch).
- EMBED message `text` is a JSON string `{title?, description[], footer?}`; the transcript reader regroups consecutive messages by player+character into Discord-style blocks.
- **Story dialogue presentation**: `Story.format` (`SCRIPT` | `PROSE`) switches script-style vs novel-style rendering. A NARRATION `StoryLine` may carry `segments` (ff-server's `story_segments` rows, served as `[{text, characterId?, personaId?, persona?, italic?, bold?}]`) — the universal inline-run primitive for embedded dialogue *and* inline italic/bold — with segment texts concatenating verbatim to `text` (server-derived, so they never desync; search/scan stay on `text`). Block section headings use the `HEADING` line type. Import: `[spoken]{Speaker}` dialogue spans, `*italic*`/`**bold**` emphasis, and `## Title` headings in the story markdown; the docx converter maps Heading 1→chapter, Heading 2→heading line in prose.
- **Story voices are personas** (2026-11-10): a story line or segment is voiced like a message, by `characterId` alone, `characterId` + one of its personas (`personaId`), or an NPC persona alone (`characterId` null). A persona restyles story quotes as it does messages: name, color and avatar each fall through `persona ?? character` (`storyVoice` in `src/lib/stories.ts`; the reader's color rule keys fallbacks on the character's own name). NPC quotes read grey unless their persona has a color, never link anywhere (name tooltip, `help` cursor), and show a head in the avatar rail only when the NPC has an avatar. `slimLine` derives the reader's `speaker`/`npcVoice`/`npc` from the persona, so don't read those fields off the API (they're deprecated there). Import: a doc color that stands for "whichever NPC is talking" (gray `#666666` defaults to it) converts to unnamed NPC voices (`[spoken]{?}` / `> ?:`, segment `npc: true` / line `npcVoice: true`); the importer's `NpcVoiceNamer` must name every one before upload: a name is an NPC persona (found or created on upload, shared by name across the archive), `@Name` gives the quote to a character and `@Name as Persona` to a character as a persona. A named speaker maps on the "speakers → characters" list to a character or a character-as-persona (exact character name first, then a character persona's name), else it uploads as an NPC of that name. A revision (same slug) pre-fills its gray quotes from the story as it stands (`POST /stories/:slug/voices/carry`). Readers change a voice from the line's action rail, never by clicking the quote (quote text only links or shows a tooltip, as in transcripts): the 🎭 button (`VoiceNamePopover` → `PATCH /api/stories/:slug/voices`; a "quote" picker when the line has several) lets the story's authors or an admin give an NPC quote another NPC name, optionally with the next quotes by the same voice, or give it to a character (as a persona or not; logged in the admin History), and lets admins change a quote a character already speaks to another character, a persona or an NPC (ff-server allows that for admins only and always logs it, `src/story/voice-targets.ts`). An NPC left with no lines anywhere is deleted. The /admin page's **Story voices** panel moves story dialogue in bulk between NPCs, characters and characters as personas (preview = dry run). `src/lib/voiceOptions.ts` builds the "Vec" / "Vec as Sascha" choices all of these list.

## Conventions
- **No MUI, no Tailwind, no component frameworks.** Hand-rolled SCSS Modules + design tokens (`src/styles/_tokens.scss`). Art direction: retro sci-fi × indie-web Neocities.
- Season tokens (`--ff1`…, `--vm`) are for that season only. Gold highlights (warnings, results, artifacts) use `--gold`/`--gold-2` (VM's colors before it went teal).
- Theming: `data-theme` attr on `<html>`, persisted in localStorage key `colorMode` (legacy-compatible). All colors via CSS custom properties — never hard-code.
- API calls go through `src/lib/api.ts` (handles the `{status, data|message}` envelope; `apiPaged` for endpoints that return `total/page/limit`).
- 4-space indent, single quotes (matches legacy codebase style).
- API-backed index pages need `export const dynamic = 'force-dynamic'` or they prerender against a dead API at build time.
- **Never use `·` (middle dot) in site text or UI** (the user's call, 2026-11-07). Don't swap in a lookalike separator glyph either (`⭑`, `•`, `∙`, `|`, `/` used as a divider, etc.), even though some older code still uses `⭑`; don't copy those. Separate items with words or punctuation ("21 of 24 episodes, 1,497 messages"), separate elements, or typography (a pixel-label span next to a title).
